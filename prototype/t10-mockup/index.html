how the search works

The board is forty bytes

Ten columns, one 32-bit word each, bit zero at the bottom row. Collision, dropping and line clearing are shifts and masks. The evaluator walks columns, never cells — which is why it scores millions of boards a second.

The gutter on the right of the board reads straight off those words: height, holes, and the evaluator's score for the position you are looking at.

A beam, layer by layer, deduplicated

Each piece in the sequence is one layer. Every surviving board expands into every legal placement; identical boards inside a layer collapse to the one that cleared more lines; the best beam states survive. The layer table on the right shows, per layer, what came in and what was kept.

The last three pieces are searched exactly. At that depth a beam buys nothing and costs solutions.

Fixed-point scoring, so numbers compare

Height, holes, transitions and wells are integers with fixed-point weights, so native and WebAssembly arrive at identical scores for identical boards. That is the only reason the reference run on the left can sit beside your own run without a correction factor.

Every figure in this page is produced by a run in this tab, except the reference run — which names the machine, the date and the runtime it came from.

What the tree is showing you

Two hundred boards survive each layer and the rest are discarded. The tree draws each surviving board as a node, edges as the placement that produced it, colour as score. Drag to pan, scroll to zoom. The question it exists to answer is whether a full tree at width 200 is legible at all.
